# Agent Benchmark Radar Web Design

**Date:** 2026-09-01  
**Status:** Implemented v1; superseded for subsequent product work by [`2026-09-01-evaluation-frontier-web-v2-design.md`](./2026-09-01-evaluation-frontier-web-v2-design.md)
**Project site:** `https://h20zhang.github.io/Agent-Benchmark-Radar/`

## Outcome

Agent Benchmark Radar becomes a two-surface publication:

- The GitHub README gives a fast, durable field overview with three accessible capability-evolution maps, the complete benchmark tables, and a clear path into the interactive site.
- The GitHub Pages site turns the canonical registry into a searchable research instrument with shareable filters, indexable benchmark pages, bilingual navigation, and explicit methodology.

Both surfaces preserve positive, direct descriptions. Public labels present current measurement strengths and next evaluation frontiers without deficit framing.

## Architecture Decision

Add an Astro static site in `web/` and deploy it through GitHub Actions. Astro builds plain HTML for discovery and benchmark detail pages, while a small client-side script adds instant filtering. The build reads `../data/benchmarks.json` directly; no copied benchmark registry is maintained inside the site.

The first deployment uses the project Pages URL rather than the account root. Astro is configured with:

```js
site: "https://h20zhang.github.io",
base: "/Agent-Benchmark-Radar"
```

All internal links pass through one base-aware URL helper. A later custom domain requires only a configuration and Pages-settings change.

### Alternatives considered

| Approach | Strength | Decision |
|---|---|---|
| Astro static HTML + small client script | Strong crawlable output, rich filtering, maintainable page generation | Selected |
| Hand-written HTML/JS generated by Python | Minimal dependencies | Declined because page templates, metadata, and bilingual routes would become harder to maintain |
| React/Vite single-page app | Flexible application UI | Declined because client-only discovery and detail content weaken first-load resilience and search visibility |

## Information Architecture

The site contains four indexable page families and one redirect entry:

| Route | Purpose |
|---|---|
| `/` | Lightweight, `noindex` language entry that forwards to `/zh/` |
| `/zh/`, `/en/` | Main Radar with all benchmarks pre-rendered and interactive filters layered on top |
| `/zh/areas/{area}/`, `/en/areas/{area}/` | Three editorial area landing pages with stable, crawlable introductions and benchmark subsets |
| `/zh/benchmarks/{id}/`, `/en/benchmarks/{id}/` | Stable benchmark detail pages generated from registry IDs |
| `/zh/methodology/`, `/en/methodology/` | Inclusion rules, field definitions, phase semantics, update process, and citation policy |

Benchmark URLs use the stable registry `id`, never a mutable display title. Chinese and English routes remain structurally symmetric.

## Explorer Experience

The explorer is the site's primary product. The complete result set is present in the initial HTML. JavaScript enhances it by updating visibility, counts, the query string, and the active-filter summary without fetching a second data copy.

Primary controls:

- Text search across name, summary, capability, environment, and protocol.
- Area and evolution-role multi-select facets.
- Release-year range and artifact availability (`paper`, `code`, `data`).
- Searchable advanced facets for capability, environment, and protocol using the registry's existing normalized slugs.
- Sort by newest release, earliest release, citation context, or name.

Filter state uses stable query parameters such as:

```text
/zh/?area=agent-memory&role=frontier&artifact=code&sort=newest
```

Values are deduplicated and serialized in a deterministic order. Reset returns to the full registry. The empty result state invites the reader to broaden conditions and keeps every control available.

Arbitrary query combinations are not emitted as crawlable links. The language home remains their canonical URL, which prevents faceted combinations from creating an indexable page explosion.

## Content and Localization

`data/benchmarks.json` remains the canonical factual registry. English summaries come directly from `summary`. The complete Chinese one-sentence descriptions already maintained in the Chinese README tables are parsed at build time by benchmark ID and validated for one-to-one coverage. This preserves the existing bilingual editorial judgment without introducing a second manually synchronized registry.

Site chrome, area introductions, phase labels, artifact labels, and methodology copy live in a small typed locale module. Machine tokens remain stable across languages; only display labels change.

Public detail pages include:

- benchmark name, area, evolution role, release date, and last verification date;
- localized summary and the registry's positive measurement-strength statement;
- capabilities, environments, protocols, and scale;
- paper, code, data, project, and other source links;
- citation context when a Semantic Scholar match exists;
- links back to the filtered area view, methodology, canonical JSON record, and GitHub explainer when available.

The registry's `coverage_gap` field remains available in the machine-readable data and is not rendered verbatim in v1. This keeps the public surface aligned with the project's positive-description rule while a future editorial pass can create bilingual next-frontier statements.

## Visual System

The interface uses an editorial research-instrument aesthetic: warm paper background, dark ink, high-contrast cobalt and signal-green accents, compact mono metadata, and generous reading width. It avoids dashboard chrome that implies model-score comparability.

The landing hero shows the registry size, three research areas, latest verification date, and an immediate search control. Area identity is expressed with color and concise typography rather than decorative illustrations. Cards prioritize benchmark name, phase, release, one-sentence measurement target, and source availability.

Responsive behavior:

- Desktop: sticky filter rail plus two-column results.
- Tablet: horizontal filter summary plus two-column results.
- Mobile: one-column results and an accessible filter disclosure panel.

All interactive controls are keyboard reachable, have visible focus, and expose labels and live result counts. Motion respects `prefers-reduced-motion`.

## README Maps

Replace each long inline defining chain with one top-down Mermaid capability map. The maps communicate evaluation evolution rather than trying to make every paper a diagram node.

Each map contains:

- an accessible `accTitle` and `accDescr`;
- the shared stages `Foundation`, `Transition`, and `Frontier`;
- no more than four capability nodes per row;
- stable `CAPABILITY-MAP` markers for validation;
- a direct link to the corresponding filtered website view below the diagram.

Paper-level links remain in the complete registry tables, where GitHub reliably renders and exposes them. Citation metadata moves from the map introduction to the complete-registry introduction because it describes table values, not map stages.

## Search and Social Metadata

Every indexable page receives:

- a unique title and description;
- absolute canonical URL and reciprocal `hreflang` links for `zh-CN`, `en`, and `x-default`;
- Open Graph and Twitter metadata;
- semantic headings and internal links;
- JSON-LD using `CollectionPage` for explorer/area pages and `Dataset` only when a benchmark exposes a data artifact, otherwise `CreativeWork`;
- membership in the generated sitemap.

`robots.txt` allows public crawling and points to the sitemap index. The root language entry is excluded from indexing. Details and editorial area pages are the primary long-tail search targets; faceted query combinations consolidate to their language home canonical.

## Deployment and Validation

The Pages workflow runs after the existing Python validation job succeeds on `main` and is also manually dispatchable. It builds `web/` with the official Astro Pages action and deploys the generated artifact using the minimum permissions: `contents: read`, `pages: write`, and `id-token: write`.

Validation covers:

- registry normalization, deterministic filtering, and query serialization with Node's built-in test runner;
- bilingual description coverage and base-aware internal URLs;
- an Astro production build with all 125 × 2 detail pages and six area pages;
- sitemap, robots, canonical, hreflang, JSON-LD, and root redirect output;
- README Mermaid accessibility markers and positive-description contracts;
- all existing Python tests and `scripts/validate_reading.py`.

The compiled `web/dist/` directory stays ignored and is never committed.

## Delivery Boundary

Version 1 deliberately centers benchmark discovery and research verification. Cross-benchmark score ranking is excluded because benchmark metrics, agents, budgets, tools, and prompts are not a common scale. A comparison workspace can be added later once its rows compare measurement design and adoption constraints rather than incompatible headline scores.
