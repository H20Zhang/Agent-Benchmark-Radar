## 方法与测量对象

VAKRA 把 BIRD 数据库转为本地可执行接口，并加入 Wikidata5M／ClapNQ 文档。SLOT 让代理组合九类通用操作；SEL 提供 26 个更专门操作；Dashboard 把计算封装成端点，工具集合按域而非全库暴露。查询通过实体和参数连边，生成 API 链以及 API→文档或文档→API 的组合；Mistral-Large-2411 生成问题，Mixtral-8x22B 辅助质量和来源可答性过滤。部分任务给自然语言政策，例如禁用回答电影问题所需的文档工具，此时合理终点是承认无法回答。调优／测试不共享原始 BIRD 查询，但不同能力设置可能共享源查询，因此各列不是同题组件消融。

编辑比较：LiveAPIBench 是论文直接扩展的可执行 API 基础；VAKRA 增加文档与 API 相互传递实体、多跳链及工具政策。与 CRAG 一类答案评测相比，它还检查调用是否恢复必要信息和是否违规。这里的演化是组合与治理约束，不是已解决动态企业权限。

## 评分与实验条件

所有模型用 LangGraph ReAct，通过 MCP 调用域内 SQLite 接口与 ChromaDB 检索，向量模型为 granite-embedding-english-r2；代理不能直接读取数据库或索引。API 的“live”是实际执行本地函数，不是随互联网漂移的生产服务。先重新执行预测调用，用信息包含检查及 GPT-OSS-120B 语义判定是否恢复所需信息；通过后再由该裁判检查最终答案依据和事实一致性，裁判温度为零。禁止来源的调用另作确定性检查，答案正确但违规仍失败。因此总体不是纯执行匹配或纯字符串评分。论文描述固定每题超时及迭代上限，却没有列出主实验具体值；可选工具缩减器是否启用也不够明确。

## 解读、局限与下一步

在同一控制器里，接口形式和推理链延长都与分数变化相关，但样本、工具集合和最终评分不同，不能把列间差异全部归因于增加一跳。总分按设置聚合，且多来源内部的跨来源题加倍权重；这里展示分项而不另造统一通过率。GPT-OSS-120B 既被测又担任裁判，需要异模型评判敏感性检查；Claude Opus 4.7 因费用只测子集。人类抽查每设置 60 题、三位评审，并非整库正确性审计。合成连边、来源排除过滤和本地确定环境都不能证明真实企业权限、动态状态或异常恢复的可靠性。

表 2 与质量研究写多来源测试 644 题，正文／附录 C.2 写 664 题并拆为 244 带策略与 420 无策略题，冲突未解决，不能给出唯一分母。正文总 API 数超过 8,000，附录 C.5 的 Dashboard 清单为 7,087；后者是接口子集，不应改成全部模型同时看到 8,000 个工具。人工审核正文说五维共 1,800 个判断，附录实际列多跳四维、多来源六维；且部分 κ 近零或为负，77%／90% 原始一致率不能解读成高可靠性的完整认证。

先固定样本清单和真实评分代码，澄清 644／664 差异与预算；在相同底层题上改变接口抽象、提供正确中间实体或替换检索结果，分开计工具合法性、信息恢复、答案正确和拒答，再用独立裁判与人工抽查验证。
